### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

This shared playbook is reached through the [Ship skill](../../ship/SKILL.md), which runs [Babysit](babysit.md) first when readiness work remains. It supports one PR or a stack. Existing authorization to merge carries through both stages.

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, not batched, each cloud where the harness offers it, runs the change the way a user would with the project's `verify-*` skill (or `control-ui` / `control-cli` from `cursor-team-kit` when installed on Cursor), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Give each the exact commit SHA to judge, pushed or still local. It reads the diff, and the verify receipt for that commit when the repo writes one, per the push gate in `playbooks/opening-a-pr.md`. It does not wait for CI. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. When the patch did not change, keep the code verdict but re-run mergeability and CI at the current head. A verdict on a local commit stays valid for its pushed head by the same rule. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `origin pr merge <pr>` or `gh pr merge <pr> --squash`. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Merge only once every CI check on the PR's current remote head has passed (`origin pr checks <pr>` or `gh pr checks <pr>`). A repo with no required checks reports a PR mergeable while its CI still runs or fails, so mergeable is not green. A check that Babysit classified as a trunk failure still blocks until the user, or the root in an autopilot, accepts it. Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready, and on GitHub only when the repo's required checks include its CI. Without required checks, GitHub's `--auto` merges at once, so wait for green CI and merge then. After a merge lands, retarget the PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.

   **Rebase test.** Rebasing for every trunk move never ends and reruns CI each time, so rebase a PR whose base is already trunk only when the code that would land was never tested. Rebase when `git merge-tree` of the head against a freshly fetched `origin/<trunk>` conflicts, when the forge refuses the merge until the branch is up to date (GitHub `mergeStateStatus` `BEHIND`), or when a path in `git diff --name-only $(git merge-base HEAD origin/<trunk>) origin/<trunk>` is a path the PR changes or a path that decides which CI runs for it. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. When trunk changed a caller of the patch or something it depends on, such as code it calls or a dependency version, run the patch's local checks on the merge result, and rebase and fix the patch only if they fail. Otherwise land the head as it is. Hold a PR rather than rebase it onto trunk a third time after it opens, and report the collision to the root in an autopilot, or to the user otherwise, so they can sequence the work. Moving a child onto trunk after its parent merges does not count.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) under the `loop` verb (the native mechanism in `references/harness/README.md`) until it reports `COMPLETE` at the ceiling. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
