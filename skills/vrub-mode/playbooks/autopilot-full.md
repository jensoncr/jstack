### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One owner agent per PR, cloud where the harness offers it, owns build, the first push, a ready PR at the code-ready head, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the `deslop` skill from the `cursor-team-kit` plugin when installed on Cursor, otherwise the **unslop** skill for prose and the **no-comments** skill for code), `/no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill and pushes its first branch snapshot. Until the PR opens, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine), so a replacement can pick up the work. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base and rebases only on a `git merge-tree` conflict with trunk or a CI failure that comes from a change on trunk. The full rebase test in `playbooks/shipping.md` step 4 runs only right before the merge (step 5). When the shipped code is final, after the slop-strip, `/no-comments`, and that rebase, the owner opens the PR ready, never draft, at that head through the push gate in `playbooks/opening-a-pr.md` and reports the code-ready head SHA. Every later push to the PR goes through the same gate. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. Babysit holds its fixes until the swarm's findings arrive, so both go out in one fix-forward push. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify once.** A full swarm runs once, at the owner's code-ready head SHA. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. A lane result that the patch-id rule in `playbooks/shipping.md` keeps valid needs no rerun. At the code-ready SHA, fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. The merge needs a clean verdict whose patch matches the merge-ready head. Audit the owner's receipts for that SHA before the verdict. CI is step 5's merge gate, not a lane input. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (the project's `verify-*` skill, or `control-ui` / `control-cli` from `cursor-team-kit` when installed on Cursor, or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the brief of whoever verifies the fix. The fix-forward goes out once, through the push gate with that verdict. **Cap review at two rounds per PR.** The full swarm is round 1, and the single verifier on the fix-forward is round 2. After round 2 the PR's code is frozen. Only a P1 or P2 finding, or a regression against trunk, reopens it, and that fix gets one narrow round that checks the fix and adds cases near it. Every other finding goes on the PR's follow-up list instead of starting a round. A lane that the environment blocks (memory, ports, a CI outage) is not a code finding. Report it to the operator as blocked rather than running another round.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** Merge prep never comes before the swarm's lanes start. Right before the merge, the owner fetches trunk and applies the rebase test in `playbooks/shipping.md` step 4, so a trunk move forces a rebase only when it can affect the patch. After a rebase, the owner reports the new head SHA, and the patch-id rule decides whether the verdict still holds. A rebase that changes the patch gets step 4's single verifier through the push gate before its push. The merge itself follows the green-CI rule in `playbooks/shipping.md` step 5. The merge needs green CI on the remote head it merges. The owner squash-merges its own PR through the resolved forge and returns. A fresh owner picks up the next self-contained item from the queue, per vrub-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm it with the `loop` verb at a 1-hour interval (`/loop 1h` where the harness has `/loop`) and a prompt that runs this tick. Without a loop, use the native continuation in `references/harness/README.md`. If none exists, keep the audit in the active session and save a handoff before ending. Do not promise unattended ticks. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk with `git show origin/main:jstack/skills/vrub-mode/playbooks/autopilot-full.md` (or read the same playbook from your jstack install) and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. An owner that holds under the rebase test, or waits on you or the operator, is not stuck. Answer it. Stand it down and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
